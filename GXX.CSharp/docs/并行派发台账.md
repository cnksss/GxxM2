## 0. 结论：可以并行，机制如下

单一工作树里跑多个 agent 必然互相踩（共用一个 git index、一次 `git add` 会把别人的半成品一起提交）。
本工程采用的方案是 **git worktree + 独占文件分区 + 单向合并**：

```
main (会话A，串行干线，持续提交)
  │
  ├─ par/lane-client-gui-mir    → .worktrees/lane-client-gui-mir    （车道1  Client GUI/Mir 窗口族）
  ├─ par/lane-resources         → .worktrees/lane-resources         （车道2  Client 资源格式族）
  ├─ par/lane-rungate-utils     → .worktrees/lane-rungate-utils     （车道3  RunGate 工具族）
  ├─ par/lane-dbserver-utils    → .worktrees/lane-dbserver-utils    （车道4  DBServer 工具族）
  ├─ par/lane-dxcomponent       → .worktrees/lane-dxcomponent       （车道5  DxComponent 基础控件族）
  ├─ par/lane-login-logdata     → .worktrees/lane-login-logdata     （车道6  LoginSrv/LogDataServer 余部）
  ├─ par/lane-client-guiconfig  → .worktrees/lane-client-guiconfig  （车道7  Client GameConfig 对话框族）
  └─ par/lane-client-statewin   → .worktrees/lane-client-statewin   （车道8  Client StateWindows.pas 分片）
```

- 每个车道 = 一个独立目录 + 一条独立分支 + 一份独立 `index`，因此**可以真正并行提交**，不会互相锁。
- 冲突面被压到零的做法有二：
  1. **文件独占分区**（见 §2）：任何两个写入者不得拥有同一个文件路径。
  2. **车道只新建文件**：SDK 风格 csproj 自动 glob 全部 `*.cs`，新增文件**不需要改 csproj / slnx**，所以车道永远不碰共享文件。
- 合并方向是**单向的**：`par/* → main`，由会话 B 在集成时执行；车道永不 merge/rebase。
- 因子工程的项目引用不跨车道，`dotnet build` 在各自目录内独立可跑（已验证：全量 build 约 3 秒）。

## 7. 工具与基线快照

### 7.1 `GXX.CSharp/tools/`

| 文件 | 作用 |
|---|---|
| `audit-coverage.ps1` | Delphi `.pas` → C# 映射审计（DoD「无未映射单元」的可执行形式）。证据：E1 同名 `.cs` / E2 某 `.cs` 头部提到 `<unit>.pas` / E3 Checklist.md 提及 / E4 `unit-map.tsv` 显式登记。判定：`MAPPED` / `ASSIGNED`（车道在飞）/ `CHECKLIST_ONLY` / `UNMAPPED` / `VENDOR`（第三方，不移植） |
| `unit-map.tsv` | 显式「单元 → 车道」登记表。车道认领某单元时在此加一行；该单元落地后被 E1/E2 识别为 `MAPPED`，即可删除该行 |
| `Merge-ParallelLanes.ps1` | 集成合并：校验主工作树干净 → 列出合并计划 → **冲突预检**（两条车道不得改同一文件）→ `git merge --no-ff` 逐条合并 → Release build + 全解决方案 test 门禁。`-DryRun` 只预览 |
| `lane-zones.tsv` | 车道文件分区（`docs/并行派发台账.md` §2 的机器可读镜像） |
| `verify-lanes.ps1` | **分区机械执行器**：对每条车道同时检查「已提交改动」与「工作树未提交改动」，报出 `OUT-OF-ZONE`（越区写）/`MODIFIED-EXISTING`（改了别人已有的文件，车道只许新增）/`SCRATCH`（`_tmp_src`、`.tmp-src`、`_recon` 等临时目录残留）。**派发后与合并前各跑一次** |
| `Register-TestProjects.ps1` | 把车道新建、但尚未登记进 `GXX.slnx` 的测试工程补进去（幂等；默认只报告，`-Apply` 才写）。合并时跑一次 |
| `gen/GenSqlCreateTable.ps1` | 建表 SQL 常量族生成器：从 `.pas` 抽取常量 → 生成 `src/GXX.Core/Data/*.cs` + 指纹测试，并跑 V1 往返 / V2 CRLF 普查 / V3 分号普查，任一不过就整体失败 |

用法：
```powershell
cd D:\chuanqi\daima\GXX原版_Delphi7
& .\GXX.CSharp\tools\verify-lanes.ps1                    # 分区体检（越区/改他人文件/临时文件残留）
& .\GXX.CSharp\tools\audit-coverage.ps1 -Report -ReportPath 'docs\并行覆盖审计.md'
& .\GXX.CSharp\tools\Merge-ParallelLanes.ps1 -DryRun
& .\GXX.CSharp\tools\Merge-ParallelLanes.ps1
```

## 8. 经验与坑（踩过就记下来，别再踩）

### 8.1 PowerShell 5.1 按 ANSI 解析 `.ps1` —— 工具脚本一律纯 ASCII

- 含中文的 `.ps1` 必须带 UTF-8 BOM；但**编辑器保存时会丢 BOM**，于是"能跑→改一行→报语法错"反复出现（本项目已踩 4 次）。
- 结论：`tools/**.ps1` **全部写成纯 ASCII**（英文注释与英文输出）。中文路径/文本**作为命令行参数传入**（命令行通道是 UTF-8 安全的），不要在脚本里写中文**字面量**——包括 `$PSScriptRoot` 拼接时也要避免中文常量。
- 反过来，**生成的 C# 文件可以是 UTF-8**（C# 编译器默认按 UTF-8 读，无 BOM 也没问题）。

### 8.2 合并期"干线有未提交改动"不一定是阻塞

车道只**新增**文件，所以只要「干线脏文件集合」与「车道改动文件集合」**交集为空**，合并就是安全的
—— `Merge-ParallelLanes.ps1` 已按这个精确判据实现（早期版本是"干线必须完全干净"，过于保守，会让并行停摆）。
`-SkipBuild` 时脚本会明确提示"集成门禁已跳过"，并给出在**车道工作树**里跑门禁的命令：
主工作树跑 `dotnet build` 会与会话 A 抢 `obj/`，**不要在主工作树构建**。

### 8.3 车道自述必须与仓库实际对照

车道6 报告：任务书里写的"`LogDataMain`/`ThreadPool`/`LDShare`/`FileSearchPool` 已移植" **与实际不符**
（`src/GXX.LogDataServer` 只有 `Program.cs` + `LogDataService.cs`）。这说明 **Checklist.md 的"已完成"不能当作事实**，
`tools/audit-coverage.ps1`（同名 `.cs` 或 `.cs` 头部引用 `<unit>.pas`）才是可核验的证据。
派发下一波前，凡"据清单说已完成"的单元都要先 grep 复核。

### 8.4 待确认的跨模块不一致（记入待办，不要擅自"统一"）

- 车道6 发现：`BasicSet` 布尔 INI 写入用 `-1`/`0`（`TIniFile.WriteBool` → `BoolToStr`），
  而 `GXX.Core/Util/FastIniFile.cs` 的 `WriteBool` 写 `1`/`0`。两者语义不同——
  需要确认原版 `FastIniFile.pas` 的真实行为后再决定是否修正，**不得凭直觉统一**。

### 8.5 未认领的两份重复副本（P2 处理）

- `ParadoxConv.pas` / `ParadoxDataSet.pas` 在 `Source/RunGate` 与 `Source/GameCenter` 各一份（同源）。
  车道3 在移植 RunGate 份；GameCenter 份暂不重复，建议 P2 把公共 Paradox 层上移到 `src/GXX.Core/**` 后共用。

### 8.6 实际发生过的越区事故与处置（必读）

- **事故**：车道3 把辅助脚本 `extract_paradox_tables.ps1` 写进了**主工作树**的 `GXX.CSharp/tools/`
  （不只是自己的 worktree）。会话 A 的 `git add -A` 随即把它扫进了 J185 提交，于是 main 上出现了这份文件；
  车道3 的分支又提交了同一路径 → 合并时会是 add/add。
  **处置**：确认两份 SHA256 完全一致（已核）；已要求车道3 用 `git rm --cached` 把该路径从分支移出。
  **教训**：`tools/**` 是集成者独占区；车道写文件必须**只用 `.worktrees/<lane>` 前缀的绝对路径**，
  写临时脚本时尤其容易图省事直接落到主工作树。

  整段屏蔽了（本意是忽略调度会话自己的登记文件），所以越区文件在干线视角是"隐形"的。
  `verify-lanes.ps1` 才是兜底 —— **派发后、合并前都必须跑**。

## 9. 集成分支与 P1 集成结果（2026-09-19/20）

### 9.1 集成分支 `par/integration`（本轮新增的关键机制）

**问题**：直接往 `main` 合车道，一旦某条车道与别的车道/干线冲突，`main` 就会处于编译不过的状态，
而 `main` 是会话 A 正在干活的分支 —— 这会直接打断它。

**做法**：新增一条**集成分支** `par/integration`（工作树 `.worktrees/integration`）作为暂存区：

```
par/lane-*  ──merge──►  par/integration  ──构建+全量测试通过后──►  main（fast-forward）
                              ▲
                       main 的新提交也先合进来（merge main）
```

于是 `main` **只会收到已经验证过的状态**，任何冲突/编译错误都止步于集成分支。

### 9.4 根因修复：`GXX.Core.HUtil32.GetValidStr3`（跨车道共性缺陷）

车道4（DBServer）与车道7（GameConfig）**各自独立**发现并绕开了同一基线缺陷，故在集成期做了根因修复。

原文 `Source/Common/HUtil32.pas:1243-1341`（Delphi 7 走 `{$ELSE}` ANSI 分支）语义：
`Dest := Str` 起步；`Len=0` 或分隔符表为空直接退出；**「丢掉最前面的分隔符，不管多少个」**；
字段内遇到第一个分隔符 → `Dest` = 字段本体（不含分隔符）、`Result` = 分隔符**之后**的剩余串；
若只有前导分隔符 → `Dest` = 去掉前导后的剩余串、`Result` = 空。

旧 C# 实现有两处误读：① 只跳前导**空格**（不跳分隔符）；② 返回的剩余串**仍以分隔符开头**
（`Copy(str, strPos, strLen)` 而 strPos 正指向分隔符）。后果：

- 以分隔符开头的行（CSV/Tab 落盘格式常见）被整行解析为空 → `FilterItems.LoadFormList` 永远加载不出物品，`DBShare`/`AddrEdit` 同类；
- `while ((s = GetValidStr3(s, ref d, div)) != "")` 这类链式切割**原地打转**。

修复后全量回归：`GXX.M2Server.Tests` 5001 项、`GXX.Client.Tests` 1870 项**全部仍通过**，
说明旧行为没有被其它模块依赖；`GXX.Core.Tests` 中 2 处**误读原文**的期望
（`GetValidStr3_Basic` 断言 `rest == ",def"` 且注释"分隔符本身保留在剩余串中"）已按原文改写，
并新增 6 条语义/链式回归守卫。
**待办**：车道4 的 `GXX.DBServer/HUtil32Seam.cs` 与车道7 的 `FilterItems.cs` 本地复刻应改为转调本方法（去重）。
